## 0. TUXMATE-ON-NIXOS VERDICT (stated plainly, up front)

**Tuxmate is NOT Arch-only. It explicitly and first-class supports NixOS (nixpkgs).** The GAP_REVIEW risk flag ("verify tuxmate isn't Arch-only before anchoring on it") is now **VERIFIED FALSE** — the Arch/AUR concern in SYNTHESIS belonged to *caelestia's* installer, not tuxmate. Tuxmate lists 10 package-manager targets: apt (Ubuntu/Debian), pacman+AUR, dnf, zypper, **Nix (nixpkgs)**, Flatpak, Snap, Homebrew. Nix is a completed roadmap item, and it ships real Nix machinery: a dedicated generator (`src/lib/scripts/nix.ts`) and an unfree-package detector (`src/lib/nixUnfree.ts` + `nix-unfree.json`, which lists `spotify`, `vscode`, etc.).

**BUT — the important qualifier — tuxmate is a *web-based command/script generator*, not an on-machine GUI installer.** It's a Next.js 16 / React 19 web app (hostable via its own Docker image, or just the public site). You pick apps in a pretty catalog and it hands you text to run yourself; it installs nothing, tracks no install-state, and offers no removal/update management. For the **Nix** target specifically, its entire output is a **declarative** snippet you paste into `configuration.nix` and then rebuild:

```nix
# Generated by tuxmate — <date>
# Unfree: spotify, vscode
# Requires: nixpkgs.config.allowUnfree = true;

environment.systemPackages = with pkgs; [
    spotify
    vscode
];
```
*(exact shape from `generateNixConfig()` in `src/lib/scripts/nix.ts` — it sorts packages, prepends the unfree comment when any selected pkg is in `nix-unfree.json`.)*

**What this means for the anchor decision:**
- ✅ Tuxmate **can be the UX north-star** (its catalog IS the "seamless/quick/pretty/mouse-first" bar MASTER §4.2 wants), and
- ✅ Tuxmate **can be a practical helper** for the declarative lane — "select VS Code + Spotify → copy the exact `environment.systemPackages` block."
- ❌ Tuxmate **cannot by itself be the on-machine 'app store'** that closes §4.2 (no install-state, no removal, no updates, no running-on-the-machine surface). It ends at "here's config to paste + rebuild."
- ⚠️ **Do not route the agent CLIs (Claude Code/Codex) through tuxmate's Nix output.** Tuxmate maps `claude-code`→`nix: "claude-code"` and `codex`→`nix: "codex"`, i.e. it would install them *declaratively from nixpkgs*, pinned to your channel and updated only on rebuild — the opposite of the `npm install -g`/instant-update experience §4.2 demands for them. The npm-global path (§2 below) owns the agent CLIs; tuxmate/GUI-store owns GUI apps. (Tuxmate's *universal* fallback does emit `npm install -g @openai/codex … && curl … claude.ai/install.sh | bash` — but only on non-Nix distros; its Nix path uses the nixpkgs attrs.)

**Verdict in one line:** Tuxmate is the right *reference* and a useful *declarative-snippet generator*, but the on-machine "install like Windows" job needs a native GUI (nix-software-center) and/or the imperative `nix profile` lane. Rankings follow.

## 1. INSTALLER-GUI COMPARISON + RANKING (§4.2, §14)

**Evaluated against tuxmate's UX bar:** seamless · quick · pretty · mouse-first — *plus* the NixOS realities (reproducible/declarative config as source of truth; read-only store).

**Previews VIEWED** (mandatory): tuxmate — catalog (light), Terminal-Preview modal (dark), Flatpak view (dark). nix-software-center — frontpage (dark), application-detail (dark), search (dark). See §6 honesty section for what I could not view.

### The honest landscape first
The NixOS community's own consensus (NixOS Discourse "Thoughts on GUI package management") is blunt: **there is no seamless "Windows-like" GUI installer for NixOS, and most attempts have failed** — because a GUI that "just installs" fights the declarative/immutable model, and one that edits your config has to guess your config's structure. So the realistic field is small, and the best answer is a *hybrid* (a pretty declarative front-end + a native store for imperative one-clicks), not a single silver bullet.

### Candidates

| # | Candidate | What it actually is | Matches tuxmate bar? | NixOS fit |
|---|-----------|---------------------|----------------------|-----------|
| **1** | **nix-software-center** (snowfallorg, was vlinkz) | Native on-machine GTK4/libadwaita/Relm4 **app store** (Rust). Explore/Installed/Updates tabs, search-as-type, per-app install-state, install/remove/update by mouse. | **Closest** — genuinely pretty & mouse-first; a real store, not a generator | Native; **declarative OR imperative** via an in-app target selector |
| **2** | **tuxmate** | Web **catalog → command/snippet generator**. Emits `environment.systemPackages` block for Nix. | Sets the bar for catalog UX; but web + copy/paste, not on-machine, no lifecycle | Declarative-only output; reproducible; no install-state |
| **3** | **`nix profile` (imperative) + thin wrapper** | The imperative install *engine*: `nix profile install nixpkgs#code`. Instant, no config edit, no rebuild; `list/remove/upgrade` supported. | Not pretty alone — but it's what a store/launcher button calls under the hood | Native; imperative (per-user profile, outside the declarative config) |
| **4** | **SnowflakeOS** | A whole beginner-focused NixOS *distro* (active but alpha) that **ships nix-software-center** as its store. | n/a — not a tool you adopt | Not adoptable into an existing build; its value = candidate #1 |
| — | GNOME Software + nix plugin · Plasma Discover + PackageKit-Nix · nix-gui | Config/PackageKit GUIs | Effectively unmaintained / experimental on NixOS | **Non-viable** — excluded (see §6, not viewed) |

### What the previews showed (findings from what I SAW, not from source)
- **nix-software-center** is a legitimate GNOME-Software clone: categorized "Explore" grid (Audio/Development/Games/Graphics/Network/Video), "Recommended" app cards showing friendly name + nixpkgs attr (e.g. `gnome-podcasts`, `kicad-small`), an **app-detail page with an `Install` button *and* a top-right target selector reading "System (configuration.nix) ▾"** — that dropdown is the declarative-vs-imperative switch, the single most important UX detail — and a search page with blue check badges marking already-installed packages. It is mouse-first and clean. **Aesthetic caveat:** it is stock libadwaita/GNOME, so it will *not* match the aurora-glass QuickShell identity and it pulls in the GTK theming surface (§4.17's job to tame). §4.2 is about *ease*, not cohesion, so this doesn't disqualify it — but flag it.
- **tuxmate** is the prettier, more modern catalog (multi-column categories, per-app per-distro availability dots, a "Terminal Preview" drawer with Copy/Download-Script, keyboard nav, light/dark). But every screenshot ends at *generated text you run yourself*.

### RANKING (best NixOS-native GUI app manager for GUI apps like VS Code/Spotify)

1. **nix-software-center — #1 native GUI app manager.** It is the only candidate that runs on the machine and gives the full browse→click→installed→update→remove loop by mouse, and it uniquely lets the *same* click go declarative (writes to `configuration.nix`) or imperative (`nix profile`). It is the closest thing NixOS has to the macOS App Store / Windows Store. **Risks to settle [live-test at execution]:** (a) its declarative writer edits `configuration.nix` via `nix-editor` — verify it cooperates with *this build's flake/module layout* rather than assuming a monolithic `configuration.nix`; (b) release cadence is stale (0.1.2, many open issues) — pin a known-good rev; (c) libadwaita theming (§4.17).
2. **tuxmate — #1 for catalog UX + declarative snippet generation, not a lifecycle manager.** Keep it as the UX reference and as the "pick apps → get the exact `environment.systemPackages` block" helper for the declarative lane. Self-host its Docker image on the box or use the site.
3. **`nix profile` (imperative) — the instant-install engine / fallback lane.** `nix profile install nixpkgs#vscode nixpkgs#spotify` installs *now*, no rebuild. Best surfaced *behind* nix-software-center's imperative mode, or as a one-line action in the launcher/Settings. Downside: imperative installs live outside the reproducible config.

### RECOMMENDED ARCHITECTURE (decisive)
Two lanes, because this build is declarative-by-design (flake/channel) yet wants Windows-ease:

- **GUI-apps default lane = DECLARATIVE, made painless.** Config stays the source of truth (reproducible, and it's what makes Task 3's diff/rollback superpower possible). Ease comes from the front-end: **tuxmate (or nix-software-center's "System (configuration.nix)" mode) to pick apps → land them in an `apps.nix` module → activate with `nh os switch` (one command, auto-shows the diff — §3).** The one unavoidable friction vs. Windows is the rebuild step; it is offset by the diff/rollback headline (§3) and reduced to a single command by `nh`.
- **On-machine mouse-first store = nix-software-center**, offered for "I just want to click and have it installed without opening a file." Run it in **imperative (`nix profile`) mode** for instant, no-rebuild installs; enable its declarative mode only after the flake-write compatibility check passes.
- **Agent CLIs never go through either** — they own the npm-global lane (§2).

This gives the §4.2 outcome: browsing a pretty catalog and clicking to install VS Code/Spotify, with a reproducible config underneath and an atomic undo on top — arguably *better* than Windows/macOS, not just equal.

## 2. DURABLE npm-GLOBAL FOR AGENT CLIs (§4.2, §13; keep Claude Code/Codex working)

**The problem (root cause).** nixpkgs' `nodejs` lives read-only in `/nix/store`. By default npm's global `prefix` points *inside* that store path, so `npm install -g …` fails ("EROFS/EACCES"). The fix is a **user-writable prefix on PATH** — then `npm install -g <agent>` behaves exactly like on any other OS. `programs.nix-ld.enable` (already on, a §10 invariant) is the second half: it lets the prebuilt/native binaries these CLIs ship or download (Claude Code's bundled ripgrep, etc.) run under NixOS.

### Concrete config shape (Home Manager — the durable form)
```nix
# home.nix (Home Manager)
{
  # 1. Writable global prefix, exported for every login shell (Fish included).
  home.sessionVariables = {
    NPM_CONFIG_PREFIX = "$HOME/.npm-global";
  };

  # 2. Put the global bin dir on PATH durably (survives rebuilds).
  home.sessionPath = [ "$HOME/.npm-global/bin" ];

  # 3. Belt-and-suspenders: pin the prefix in ~/.npmrc too, so npm honors it
  #    even for non-login/!session-var contexts.
  home.file.".npmrc".text = ''
    prefix=''${HOME}/.npm-global
  '';

  # 4. Pin ONE Node so the global store never breaks under a version swap.
  #    (Community warning: global npm tools "disappear"/break when the active
  #     node major changes. A single system node keeps the prefix consistent.)
  home.packages = [ pkgs.nodejs_22 ];   # or pin at NixOS environment.systemPackages
}
```
Channel-based equivalent (no Home Manager): set the same `prefix=~/.npm-global` in `~/.npmrc` and add `~/.npm-global/bin` to PATH via `environment.sessionVariables`/shell init; put `nodejs_22` in `environment.systemPackages`.

**Fish caveat [live-test at execution]:** `home.sessionVariables`/`home.sessionPath` are exported through `hm-session-vars.sh`, which Home Manager's Fish integration sources — but Fish has historically been finicky about this. At execution, confirm in a fresh Fish: `echo $NPM_CONFIG_PREFIX` and `which claude codex` resolve into `~/.npm-global/bin`. If not, add an explicit `fish_add_path ~/.npm-global/bin` via `programs.fish.shellInit`.

### The update flow (works like any other OS)
```bash
# Update both agents to latest — this is the "as easy as npm install -g" experience:
npm install -g @anthropic-ai/claude-code@latest @openai/codex@latest
#   or:  npm update -g @anthropic-ai/claude-code @openai/codex
```
- Because the prefix is user-writable, **Claude Code's own `claude update` self-updater also works** (it writes into `~/.npm-global`, not the store).
- First-time (re)install after wiring the prefix: `npm install -g @anthropic-ai/claude-code @openai/codex`.
- **No `nixos-rebuild` is ever needed to update the agents** — that's the whole point, and it decouples agent freshness from the system-update cadence.

**Note the deliberate divergence from nixpkgs:** nixpkgs *does* ship a `claude-code` package, but it tracks the channel and updates only on rebuild — so it does **not** meet the "instant, like npm -g" bar. Keep the agents on the npm-global lane, not `environment.systemPackages`. (Alternatives that also stay fresh, if the npm lane ever regresses: community flakes `sadjow/claude-code-nix` (hourly-updated) and `kumulustech/claude-nix` (npm auto-update in the user dir) — bonus, §5.)

## 3. UPDATE-DIFF + ROLLBACK MECHANISM (C3 — the "better than Windows/macOS" headline)

**The claim C3 makes is real and I can source every step:** NixOS is the only OS that can show *exactly* what an update changed — packages added/removed and version bumps — and undo it *atomically*. Below is the mechanism (commands + tool sourcing) for a Settings › System "update" flow. **The UI is a separate session's job; this supplies the engine and command shapes.**

### 3a. The core flow: check → build → SHOW DIFF → activate

```bash
# (1) CHECK / refresh inputs
#   channel:  sudo nix-channel --update
#   flake:    nix flake update            # (or: nix flake lock --update-input nixpkgs)

# (2) BUILD the new system WITHOUT activating it — arrives as ./result
#   channel:  nixos-rebuild build
#   flake:    nixos-rebuild build --flake .#macbook
#             (equiv: nix build .#nixosConfigurations.macbook.config.system.build.toplevel)

# (3) SHOW THE DIFF — what this update actually does:
nvd diff /run/current-system ./result          # pretty, grouped: added / removed / upgraded (<old> -> <new>)
#   built-in, zero-dependency equivalent:
nix store diff-closures /run/current-system ./result

# (4) ACTIVATE:
sudo nixos-rebuild switch [--flake .#macbook]   # activate now + set as boot default
#   or defer to next boot without changing the running system:
sudo nixos-rebuild boot  [--flake .#macbook]
```

**Diff-tool sourcing (all produce the "added/removed/version-bump" report C3 asks for):**
- **`nvd diff <A> <B>`** — the community-standard version-diff tool (canonical home `~khumba/nvd`, sourcehut; nixpkgs attr **`nvd`**). Groups store paths into **Added / Removed / Upgraded** with `pkg  <oldver> -> <newver>`. This is the canonical `nixos-rebuild build && nvd diff /run/current-system result` workflow.
- **`nix store diff-closures <A> <B>`** — **built into Nix itself**, no extra package. Same information (version changes + closure size deltas). Use this if you want zero dependencies. *(Bonus, §5.)*
- Diff any two *generations* directly: `nvd diff /nix/var/nix/profiles/system-{41,42}-link`.

### 3b. The recommended wrapper — `nh` (nix-community/nh) does check→build→diff→activate in one command

**`nh` is the "nixos-rebuild wrapper that shows the generation diff" C3 wants, already built.** It wraps `nixos-rebuild` and **automatically prints the closure diff after every build** — no manual `nvd` step:

```bash
nh os switch    # build + AUTO-SHOW DIFF + activate now, set boot default
nh os boot      # build + AUTO-SHOW DIFF + activate on next boot
nh os build     # build + AUTO-SHOW DIFF only (dry preview — ideal for a "Check for updates" button)
```
Enable it declaratively:
```nix
programs.nh = {
  enable = true;
  flake = "/home/alex/nix";     # so nh os switch needs no path arg
  # clean.enable = true; clean.extraArgs = "--keep-since 4d --keep 3";  # ties into B6 GC
};
```
- **Version note [current as of 2026-07]:** nh **v4.4.1** (July 2026, actively maintained) renders diffs via **`dix`** (a faster nvd-class closure differ) and build trees via **`nix-output-monitor` (nom)**. Older nh used **`nvd`** directly. For the Settings UI this is an implementation detail — all three (`dix`, `nvd`, `nix store diff-closures`) yield the same added/removed/upgraded semantics. The UI can shell out to `nh os build` and parse/echo its diff, or call `nvd`/`diff-closures` directly for a structured parse.

**Mechanism handoff to the Settings session:** "Check for updates" = `nh os build` (or step 1+2 then `nvd diff`) → render the diff → "Update" button = `nh os switch` → "Update at next boot" = `nh os boot`.

### 3c. Rollback — atomic, boot-selectable (the undo superpower)

Every `switch`/`boot` creates an immutable generation at `/nix/var/nix/profiles/system-<N>-link` **and** a systemd-boot menu entry ("NixOS — Configuration <N>"). Because MASTER §4.4 hides that menu (timeout 0, hold-to-reveal), a **GUI rollback button is essential** — it's the mouse-first path to the entry the user can no longer see at boot.

```bash
# List generations (dates, current marker) — for the Settings "history" list:
nixos-rebuild list-generations
#   or: sudo nix-env --list-generations -p /nix/var/nix/profiles/system

# ROLLBACK NOW (activate previous generation immediately, no reboot):
sudo nixos-rebuild switch --rollback

# ROLLBACK AS BOOT DEFAULT (C3's exact wording: "boot-selects the previous generation")
# — set previous gen as the default boot entry, take effect next boot, running system untouched:
sudo nixos-rebuild boot --rollback

# Roll to a SPECIFIC earlier generation N and make it the boot default:
sudo nix-env --switch-generation <N> -p /nix/var/nix/profiles/system
sudo /nix/var/nix/profiles/system-<N>-link/bin/switch-to-configuration boot
#   (activation type `boot` = reinstall bootloader entries + set this gen default, do NOT switch the live system)
#   use `… switch-to-configuration switch` instead to also activate it right now.
```
- **`nixos-rebuild switch --rollback`** → the "Roll back now" button (instant, atomic; no build).
- **`nixos-rebuild boot --rollback`** (or `switch-to-configuration boot` on a chosen gen link) → C3's literal "rollback button that boot-selects the previous generation."
- The always-present safety floor (per §15 / MASTER §4.4): the systemd-boot menu still lists every generation for recovery even if the GUI is dead — hold a key at boot. So "lockout" is never a brick.

**Ties into:** B6 (GC policy must not delete the generation the rollback button targets — keep last N + known-good pin) and B7 (this whole flow lives in Settings › System).

## 5. BONUS FINDS (flagged; §8 permits surfacing beyond the ask)

1. **`nh` is the single highest-leverage adoption here** — it collapses C3's entire "check → build → diff → activate" into `nh os switch`/`nh os boot`/`nh os build` with the diff shown automatically, *and* its `clean` subcommand is a ready answer to B6's GC policy (`--keep-since 4d --keep 3`). One tool serves C3 + B6. Strongly recommend the plan adopt `programs.nh`.
2. **`nix store diff-closures` is a zero-dependency diff** — if the Settings UI wants to avoid pulling `nvd`/`dix`, Nix itself already produces the added/removed/version-bump report. Good for a minimal-dependency implementation.
3. **Declarative-vs-imperative as a *visible UX choice*** (the exact trick §4.2/§14 reward): nix-software-center's "System (configuration.nix) ▾" selector proves the pattern — one install button, user picks "permanent (in config, reproducible)" vs "just for now (nix profile)". This is a genuinely better-than-Windows affordance and should be mirrored anywhere the build offers an install action (store, launcher, Settings).
4. **`nix run` / `nix shell nixpkgs#<pkg>` = "try without installing"** — run an app once without adding it anywhere. Windows/macOS have no clean equivalent; a "Run once" affordance in the launcher/store is a cheap delight.
5. **Always-fresh agent-CLI flakes as a backup lane** — `sadjow/claude-code-nix` (hourly-updated Nix package) and `kumulustech/claude-nix` (user-dir install, npm auto-update) exist if the npm-global lane ever regresses; keeps the "always latest Claude Code" guarantee without npm.
6. **Tuxmate is self-hostable on the box** (`docker run … ghcr.io/abusoww/tuxmate`, or `npm run build && npm start`) — if an offline/local catalog is ever wanted, the UX reference can literally run as a local web app; its app registry (`src/lib/apps/*.json`) is also a ready-made curated catalog of nixpkgs attrs to seed a bespoke picker.
7. **`nixos-rebuild build-vm`** builds a throwaway VM of the *new* config — a "test this update in a sandbox before I commit" button, beyond even rollback. Deep-cut, but on-theme for "better than Windows."
